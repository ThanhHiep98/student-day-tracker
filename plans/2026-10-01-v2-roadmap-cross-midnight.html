Build the screens a student sees to create an account and sign in with Google, and the account controls inside the app. The approved designs ①–⑧ in §1.2 are the target the implementer must match.

Trong scope:

  • Auth gate (auth-gate.tsx, client): skeleton while Firebase restores the session (no flash of ①), sign-in screen when signed out, app shell when signed in. /privacy/ is reachable signed out.

2. Backend — Tạo account + đăng nhập (F2)

Supersedes the F2 sketch in plans/2026-10-01-firebase-setup.html where they differ · console prerequisites U2–U6 done 2026-10-02/03 · JDK 21 installed locally · Firebase project student-day-tracker, tests use demo-sdt

2.1 Scope

A student signs in with Google; the first sign-in creates the account. Data then lives in Firestore under users/{uid}, syncs across devices and works offline. Pure helpers (build*, get-*, Insights) are unchanged; only the data layer, hooks and writes change.

Trong scope:

  • Firebase Auth (Google provider only) + use-auth; profile document users/{uid} created on first sign-in
  • Firestore (persistentLocalCache + multi-tab) replaces Dexie as source of truth; use-* hooks keep their names/return shapes, writes take a UserScope
  • One-time Dexie → Firestore migration (custom categories + non-demo activities incl. spanId pairs) — batches ≤ 500, repeat-safe, markers written last; Dexie stays read-only (frozen at version(2))
  • Sign out clears the local Firestore cache; Security Rules + rules tests; Auth/Firestore emulators for dev, integration and e2e; CI runs the emulator tests (Java 21)
  • Service worker stops intercepting Firebase traffic

Ngoài scope (explicit):

  • Email/password, SMS, anonymous/guest mode; account deletion (Q2); parent sharing
  • App Check wiring (ReCaptchaEnterpriseProvider, site key 6LfvG9stAAAAAJ5N4S63oaDKwUsVCZtNdn0bC0lc, not enforced) and AI — both F3
  • New default categories / goal mapping (D-B = (iii), slice 2)

Implementation notes that change what gets built.
  • firebase.ts: lazy singletons (never initialise at module top level — static export prerenders in Node). initializeFirestore(app, { localCache: persistentLocalCache({ tabManager: persistentMultipleTabManager() }), ignoreUndefinedProperties: true }); memoryLocalCache() when typeof window === 'undefined' (emulator tests in Node).
  • Emulators: when NEXT_PUBLIC_FIREBASE_EMULATORS === '1' and the host is localhost/127.0.0.1 (or Node): projectId: 'demo-sdt', connectAuthEmulator(auth, 'http://127.0.0.1:9099', { disableWarnings: true }), connectFirestoreEmulator(db, '127.0.0.1', 8080), and expose window.__sdtTest = { signIn(uid, email, name), dexie } (signInWithCredential + GoogleAuthProvider.credential(JSON.stringify({ sub, email, email_verified: true, name }))). The branch is dead code in production builds.
  • Never await a commit() in a UI path: offline it resolves only on server ack. Writes return after queuing; trackWrite(promise) feeds useSyncStatus() ('synced' | 'pending' | 'offline' | 'error', module store + useSyncExternalStore). Builders still throw synchronously, so inline form errors keep working. Only migration awaits commits (online, 30 s timeout per batch).
  • Queries filter on one field and sort client-side: where('date','==',d) then sort by startMinutes; range = where('date','>=',s) + where('date','<=',e); span lookup where('spanId','==',id). No composite indexes, no firestore.indexes.json.
  • getActivityRows reads getDocsFromCache first (works offline; rows are already subscribed), falling back to getDocs. Edit/delete use writeBatch (works offline), not runTransaction.
  • src/app/sw.ts: prepend { matcher: ({ url }) => url.hostname.endsWith('googleapis.com') || url.pathname.startsWith('/__/'), handler: new NetworkOnly() } before defaultCache — its cross-origin NetworkFirst rule would otherwise cache Firestore/Auth GETs.
// firestore.rules (sketch — tests in tests/rules/ are the spec)
rules_version = '2';
service cloud.firestore {
  match /databases/{database}/documents {
    function isOwner(uid) { return request.auth != null && request.auth.uid == uid; }
    function str(v, max) { return v is string && v.size() >= 1 && v.size() <= max; }
    match /users/{uid} {
      allow read: if isOwner(uid);
      allow create: if isOwner(uid) && validProfile(request.resource.data);
      allow update: if isOwner(uid) && validProfile(request.resource.data)
        && request.resource.data.diff(resource.data).affectedKeys()
             .hasOnly(['migratedFromDexieAt', 'displayName', 'photoURL']);
      match /activities/{id} {
        allow read, delete: if isOwner(uid);
        allow create, update: if isOwner(uid) && validActivity(id, request.resource.data);
      }
      match /categories/{id} {
        allow read, delete: if isOwner(uid);
        allow create, update: if isOwner(uid) && validCategory(id, request.resource.data);
      }
    }
  }
}

S1.1 Scope

Log an activity from 21:00 on one day to 01:00 the next, and have each day count only its own part.

Trong scope:

  • Start date field on the Add/Edit form; end < start means “ends next day”
  • Storage as two per-day rows linked by spanId; edit/delete act on the whole span
  • Timeline labels for both halves; Insights counts a span as one session
  • Dexie version(2) adding only the spanId index

Ngoài scope (explicit):

  • Onboarding, goals, warnings, ratings, stickers, accounts
  • Overlap detection; editing from History (History stays read-only)

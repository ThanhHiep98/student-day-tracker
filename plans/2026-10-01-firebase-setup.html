Plan: Firebase setup — user console steps + F1 Hosting & CI

2026-10-01 · decision: architecture/ADR-007-firebase.md (supersedes ADR-001 in docs/DECISIONS.md; resolves D-A; use-case + activity diagrams there) · roadmap: plans/2026-10-01-v2-roadmap-cross-midnight.html · requirement: requirement/Requirement.txt (“Tạo User và đăng nhập”), docs/REQUIREMENTS.md §4 · F1 phase A: implementer can run now · F1 phase B waits for the user's “done”

Scope

ADR-007 is split into three sub-slices. F1 is planned in full here: serve the existing static export from Firebase Hosting, deploy from GitHub Actions (live on merge to master, a preview channel per PR), and retire GitHub Pages. F1 does not use the Firebase SDK and has no runtime behaviour change, so the app stays Dexie-backed. F2 (Auth + Firestore + migration + rules) and F3 (AI comments) are only scoped here. Each gets its own plan later. Everything stays on the Spark plan (no billing). Hosting, preview channels, custom domains, Google sign-in, Firestore, and AI Logic with the Gemini Developer API all work without billing. Not in F1: the Firebase JS SDK, sign-in, Firestore, App Check, and AI.

Order: cross-midnight (slice 1) before the Firestore migration? Confirmed: yes

SequenceWhy
Slice 1 ∥ F1 → F2 → slices 2, 3, 4 → F3 → 5, 6 (1) Data moves to Firestore once, already in its final shape (spanId, end 1–1440). Without Cloud Functions, a later shape change would need a client-side migration of every user's cloud data. (2) Slice 1 is planned and unblocked, while F2 is blocked on the user, so doing slice 1 first loses no time. (3) F1 touches only deploy config, so it runs in parallel with slice 1 and doesn't conflict. (4) Slices 2–4 come after F2, so their new stores (profile, ratings) are written once, directly in Firestore under users/{uid}, not built in Dexie and then ported. (5) F3 comes after slice 4 because slice 4's rule-based comments are F3's offline/over-quota fallback.
Cost of this orderSlice 1 adds a Dexie version(2) index that F2 later throws away. It is one line and needs no upgrade function, so the cost is small.

F1 — Success criteria

Gradeable now (phase A, no credentials)

  • ☐ pnpm typecheck, pnpm check, pnpm test, pnpm build, pnpm test:e2e all pass.
  • ☐ pnpm build && pnpm test:e2e:hosting passes against the hosting emulator with project demo-sdt, and no firebase login is needed.
  • ☐ Hosted /, /history/, /insights/ return 200. /history redirects to /history/. An unknown path returns 404.
  • ☐ /sw.js returns Cache-Control: no-cache. A /_next/static/ asset returns max-age=31536000, immutable.
  • ☐ The manifest start_url and scope are /, and out/ contains no /student-day-tracker/ prefix.
  • ☐ No GITHUB_PAGES or basePath reference remains in src/ or next.config.ts, and .github/workflows/deploy.yml is deleted.
  • ☐ playwright.config.ts ignores hosting.spec.ts, so the default E2E run doesn't need the emulator.
  • ☐ 0 axe violations on hosted / and on all routes in the dev run.
  • ☐ No Firebase SDK in package.json dependencies (F1 is deploy-only). No secrets, service-account JSON, or tokens are committed.

Gradeable after the user's “done” (phase B)

  • ☐ .firebaserc points at the user's project ID, and firebase.json still matches A2.
  • ☐ Both workflows use pnpm, run typecheck/check/test/build before deploying, reference the secret only by name, and skip forks on PRs.
  • ☐ A PR gets a bot comment with a working preview URL (expires in 7 days).
  • ☐ After merge, https://<projectId>.web.app serves the app, and hosting.spec.ts passes against it.
  • ☐ The README and ARCHITECTURE show the live URL. The U9 answer (real data on github.io: yes/no) is recorded, and GitHub Pages is unpublished if the answer is no.
